# 🐳 Настройка контейнера — Среда разработки opencode

> **Запустите opencode в изолированном, воспроизводимом контейнере со всеми заранее установленными зависимостями.**

Это руководство проведёт вас через настройку и использование контейнера Podman для opencode с нуля. Опыт работы с контейнерами не требуется.

---

## 📋 Предварительные требования

| Требование | Зачем |
|------------|-------|
| **Podman** | Рантайм контейнеров (прямая замена Docker) |
| **Git** | Клонирование репозитория конфигурации |
| **Интернет** | Первая сборка загружает ~1 ГБ пакетов |

### Установка Podman

```bash
# Fedora / RHEL
sudo dnf install -y podman

# Ubuntu / Debian
sudo apt install -y podman

# macOS (Apple Silicon или Intel)
brew install podman
podman machine init
podman machine start

# Arch
sudo pacman -S podman
```

### Проверка

```bash
podman --version
# podman version 5.x.x или новее
```

## ⚡ Быстрый старт (3 команды)

```bash
# 1. Клонируйте конфигурацию (в ЛЮБОЙ каталог — НЕ в ваш настоящий ~/.config/opencode)
git clone <your-repo-url> ~/opencode-container
cd ~/opencode-container

# 2. Соберите образ (только первый раз — займёт несколько минут)
./scripts/launcher.sh --build

# 3. Вы внутри. Запустите opencode в контейнере.
opencode
```

Вот и всё. Лаунчер делает всё: сборку образа, настройку API-ключа, монтирование рабочей области, поддержку буфера обмена.

**Ваш первый проект** — лаунчер переносит вас в bash-оболочку внутри контейнера. Выберите свой путь:

🆕 **Новый проект** — создайте его, перейдите в него и начните работать:

```bash
create-project my-api      # создаёт (git, конфигурацию проекта, codegraph)
cd my-api                  # перейдите в него
opencode                   # начните работать
```

📂 **Существующий проект** — смонтируйте папку проектов, перейдите в него и подключите:

```bash
./scripts/launcher.sh ~/code    # на хосте — смонтируйте папку проектов

cd /workspace/my-api            # внутри контейнера — перейдите в проект
setup-project                   # инициализирует OpenSpec и CodeGraph
opencode                        # начните работать
```

> **⚠️ Важно:** Клонируйте в **отдельный каталог** (например, `~/opencode-container`), а НЕ в `~/.config/opencode`. Контейнер собирает собственную копию конфигурации во время сборки. Ваш `~/.config/opencode` на хосте остаётся нетронутым.

## 🔧 Подробная настройка — Пошагово

### Шаг 1: Установите Podman

Смотрите раздел [Предварительные требования](#-предварительные-требования) выше.

### Шаг 2: Клонируйте конфигурацию

```bash
# Клонируйте в выделенный каталог — НЕ в ваш настоящий ~/.config/opencode
git clone <your-repo-url> ~/opencode-container
cd ~/opencode-container
```

> **Зачем отдельный каталог?** Containerfile копирует файлы из клонаированного каталога в образ во время сборки. Ваш `~/.config/opencode` на хосте никогда не затрагивается. Можете назвать каталог как угодно.

### Шаг 3: Соберите образ контейнера

```bash
./scripts/launcher.sh --build
```

При первом запуске вы увидите:
```
🔨 Force building image 'opencode-env'...
   Containerfile: /home/allen/.config/opencode/Containerfile

[build output...]
✅ Image built successfully.
```

Это займёт 3-10 минут в зависимости от вашего компьютера и скорости интернета. Последующие запуски мгновенные (кэшированные слои).

### Шаг 4: API-ключ Tavily

При первом запуске лаунчер запросит ваш API-ключ [Tavily](https://tavily.com):

```
🔑 Tavily API key not found.
   Tavily is needed for web search in opencode.

   Enter your Tavily API key (or press Enter to skip): tvly-xxxxx
   ✅ Key saved to /home/allen/.config/opencode/.secrets/tavily.key
```

Ключ сохраняется в вашем клонаированном каталоге в `.secrets/tavily.key` и монтируется в контейнер в режиме только для чтения. Вы можете пропустить это, если не нужен веб-поиск.

### Шаг 5: Начните работу

Вы попадаете в bash-шелл внутри контейнера в `/workspace`:

```
🚀 Launching opencode container...

   Workspace:      /home/allen → /workspace
   State volume:   opencode-state → /home/allen/.config/opencode/data
   Config:         baked into image (not mounted from host)
   User:           1000:1000
   Hostname:       opencode-env
```

**Что дальше?**
- 🆕 **Новый проект:** выполните `create-project my-api` → `cd my-api` → `opencode` (см. [Создание нового проекта](#создание-нового-проекта)).
- 📂 **Существующий проект:** перезапустите с его путём — `./scripts/launcher.sh /path/to/my/project` — затем `setup-project` и `opencode` (см. [Открытие существующего проекта](#открытие-существующего-проекта)).

## 🖥️ Запуск контейнера

### Базовое использование

```bash
# Запуск в текущем каталоге
./scripts/launcher.sh

# Запуск в конкретном каталоге
./scripts/launcher.sh /path/to/my/project

# Принудительная пересборка образа, затем запуск
./scripts/launcher.sh --build

# Комбинация опций
./scripts/launcher.sh /my/project --build
```

### Опции лаунчера

| Опция | Описание |
|-------|----------|
| `--build` | Принудительная пересборка образа перед запуском |
| `--help` | Показать справку |
| `WORKSPACE_DIR` | Каталог для монтирования как `/workspace` (по умолчанию: текущий каталог) |
| `-- EXTRA_ARGS` | Дополнительные аргументы `podman run` |

### Что делает лаунчер

1. ✅ Проверяет, установлен ли Podman
2. ✅ Собирает образ, если его нет (или передан `--build`)
3. ✅ Запрашивает API-ключ Tavily при первом запуске
4. ✅ Монтирует ваш рабочий каталог как `/workspace`
5. ✅ Монтирует файл секретов в режиме только для чтения
6. ✅ Включает поддержку буфера обмена (сокет X11, если доступен)
7. ✅ Маппит ваш UID хоста в контейнер (без файлов с владельцем root)
8. ✅ Опускает вас в bash-шелл

### Передача дополнительных аргументов

```bash
# Передача переменных окружения
./scripts/launcher.sh -- --env MY_VAR=value

# Установка пользовательского имени хоста
./scripts/launcher.sh -- --hostname my-dev
```

## 📁 Работа внутри контейнера

### Создание нового проекта

```bash
create-project my-api
```

Создаётся:
- Каталог `my-api/` с инициализированным git
- `README.md` с шаблоном
- Файл конфигурации `.opencode/opencode.json`
- Индекс Codegraph (если доступен)

**Опции:**
```bash
create-project my-api --no-git          # Пропустить инициализацию git
create-project my-api --no-codegraph    # Пропустить инициализацию codegraph
create-project my-api --dir ~/projects  # Создать в конкретном родительском каталоге
```

### Открытие существующего проекта

Смонтируйте любой существующий проект как `/workspace`, передав его путь лаунчеру:

```bash
# На хосте
./scripts/launcher.sh /path/to/my/project
```

Вы попадёте в корень проекта внутри контейнера. Подключите его к opencode:

```bash
# 1. Инициализируйте OpenSpec + CodeGraph для этого каталога
setup-project

# 2. Начните работать
opencode
```

**Что делает `setup-project`** — инициализирует две вещи, необходимые агентам для эффективной работы с существующей кодовой базой:

- **OpenSpec** (`openspec init`) — разработка по спецификациям: структура `openspec/` (конфиг, изменения, спецификации) плюс инструменты OpenCode в `.opencode/`
- **CodeGraph** (`codegraph init`) — индексирует кодовую базу (`.codegraph/`), чтобы агенты могли исследовать символы, цепочки вызовов и зону поражения

Повторный запуск безопасен — обе утилиты идемпотентны. Передайте каталог, чтобы указать на что-то отличное от текущего (`setup-project /path/to/project`).

> Файлы **двунаправленные** — правки, сделанные внутри контейнера, появляются на хосте и наоборот.

### Запуск opencode

```bash
opencode
```

Запускает TUI. Все агенты, скиллы и MCP-серверы загружаются из образа — настройка не требуется.

### Работа с файлами

Ваша рабочая область (`~/` на хосте) монтируется в `/workspace` внутри контейнера. **Файлы двунаправленные** — изменения, которые вы делаете внутри контейнера, появляются на хосте и наоборот.

```bash
# Внутри контейнера
cd /workspace
ls                  # Посмотрите ваши файлы хоста
opencode            # Запустите TUI
git status          # Git работает как обычно
pnpm install        # Установите зависимости
```

### Поддержка буфера обмена

Если вы на настольном Linux с X11, операции буфера обмена работают автоматически. Лаунчер монтирует сокет X11 и файл Xauthority.

## ⚙️ Конфигурация

### Как работает конфигурация

**Конфигурация контейнера УПРАВЛЯЕТСЯ образом контейнера.** Это означает:

- ✅ Агенты, скиллы, конфигурации MCP и `AGENTS.md` встраиваются в образ во время сборки
- ✅ Они всегда согласованы — каждая сборка получает одинаковую конфигурацию
- ❌ Изменения конфигурационных файлов внутри контейнера **не влияют на хост**
- ❌ Изменения конфигурационных файлов на хосте **не влияют на контейнер**

Это намеренно. Контейнер — это воспроизводимая, изолированная среда.

### Обновление конфигурации контейнера

Чтобы обновить конфигурацию, поставляемую с контейнером:

1. **Отредактируйте файлы на хосте** (в вашем клонаированном каталоге, например, `~/opencode-container/`)
2. **Пересоберите образ:**

```bash
./scripts/launcher.sh --build
```

Это подхватит изменения конфигурации с хоста и встроит их в новый образ.

### Управление секретами

Секреты обрабатываются отдельно от конфигурации — они **монтируются во время выполнения**, а не встраиваются.

| Секрет | Расположение | Как монтируется |
|--------|--------------|-----------------|
| API-ключ Tavily | `<cloned-dir>/.secrets/tavily.key` | Bind-mount в режиме только для чтения |

**Правила:**
- Каталог `.secrets/` **никогда не коммитится в git** (проверьте ваш `.gitignore`)
- Секреты монтируются в режиме только для чтения — контейнер может читать, но не изменять
- Если вы пропустите запрос API-ключа Tavily, веб-поиск не будет работать (вы можете добавить его позже, создав файл)

**Чтобы добавить ключ позже:**
```bash
# На хосте — в вашем клонаированном каталоге
mkdir -p ~/opencode-container/.secrets
echo -n "tvly-your-key-here" > ~/opencode-container/.secrets/tavily.key
chmod 600 ~/opencode-container/.secrets/tavily.key
```

## 🏛️ Архитектура

### Что монтируется (Хост → Контейнер)

| Путь хоста | Путь контейнера | Режим |
|-------------|-----------------|-------|
| `~/` (или указанный каталог) | `/workspace` | Чтение/Запись |
| `<cloned-dir>/.secrets/tavily.key` | `/home/allen/.config/opencode/.secrets/tavily.key` | Только для чтения |
| `/tmp/.X11-unix` | `/tmp/.X11-unix` | Чтение/Запись (если X11 доступен) |
| `~/.Xauthority` | `/home/allen/.Xauthority` | Чтение/Запись (если X11 доступен) |

### Что встроено в образ

| Компонент | Путь в контейнере |
|-----------|-------------------|
| Агенты | `/home/allen/.config/opencode/agents/` |
| Скиллы | `/home/allen/.config/opencode/skills/` |
| AGENTS.md | `/home/allen/.config/opencode/AGENTS.md` |
| Конфигурация opencode | `/home/allen/.config/opencode/opencode.jsonc` |
| Зависимости пакетов | `/home/allen/.config/opencode/node_modules/` |
| Скрипты | `/usr/local/bin/first-run`, `/usr/local/bin/create-project`, `/usr/local/bin/setup-project` |

### Постоянное состояние

Именованный том (`opencode-state`) хранит:
- `state_store.db` — состояние сессии opencode
- Кэш `node_modules/` — более быстрые последующие установки

Это переживает пересборку контейнера.

### Маппинг пользователя

Контейнер работает от имени пользователя без root (`allen`, UID 1000) с `--userns keep-id`. Ваш UID хоста маппится в контейнер, поэтому файлы, которые вы создаёте внутри, имеют правильного владельца на хосте.

## 🔍 Устранение неполадок

### "podman is not installed or not in PATH"

```bash
# Проверьте установку
podman --version

# Если не найден, установите:
# Fedora:   sudo dnf install podman
# Ubuntu:   sudo apt install podman
# macOS:    brew install podman && podman machine init && podman machine start
```

### Сборка завершается с ошибкой "permission denied"

```bash
# Если используете rootless podman, убедитесь, что ваш пользователь в нужной группе
# (обычно автоматически в современных дистрибутивах)
# Попробуйте собрать явно:
podman build -t opencode-env -f Containerfile .
```

### "Tavily search won't work"

Вы пропустили запрос API-ключа или файл не существует. Добавьте его вручную:

```bash
# В вашем клонаированном каталоге (например, ~/opencode-container)
mkdir -p .secrets
echo -n "tvly-your-key" > .secrets/tavily.key
chmod 600 .secrets/tavily.key
```

Затем перезапустите контейнер — он автоматически подхватит ключ.

### Буфер обмена не работает (xclip внутри контейнера)

Убедитесь, что X11 доступен:

```bash
# На хосте проверьте, запущен ли X11
echo $DISPLAY
ls /tmp/.X11-unix/

# Если пусто, X11 не запущен — буфер обмена не будет работать внутри контейнера
# Это ожидаемо на серверах без графического интерфейса
```

### Контейнер не видит мои файлы

Убедитесь, что вы передаёте правильный каталог:

```bash
# По умолчанию: монтирует текущий каталог
cd ~/my-project
./scripts/launcher.sh

# Или укажите явно
./scripts/launcher.sh ~/my-project
```

### Настройка первого запуска занимает много времени

При первом запуске выполняется `pnpm install` для зависимостей конфигурации. Последующие запуски пропускают это (кэшируется через файл-маркер `.initialized`).

### Конфигурация контейнера устарела

Если вы обновили файлы на хосте и хотите, чтобы они были в контейнере:

```bash
./scripts/launcher.sh --build
```

Это пересобирает образ, подхватывая все изменения с хоста.

### "opencode: command not found" внутри контейнера

Образ мог устареть. Пересоберите:

```bash
./scripts/launcher.sh --build
```

### Сборка образа медленная

Первая сборка загружает ~1 ГБ пакетов. Последующие сборки используют кэширование слоёв Podman и пересобирают только изменённые слои (обычно секунды).
